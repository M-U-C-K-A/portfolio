A persistent misconception in the web development world is that an accessible site must necessarily be "ugly" or stripped down. In 2026, with the tools at our disposal, it is a myth that it is time to deconstruct.

Accessibility is not a checklist of constraints that curb your creativity, it is a framework that pushes for smarter and more robust design. Let's see how to handle two of the most complex components: the **Modal** and **Drag & Drop**.

---

## 1. The Modal: Taming the Focus

A poorly designed modal is an insurmountable wall for a user navigating with a keyboard or screen reader. To be accessible, it must respect three technical golden rules.

### The Focus Trap
When a modal is open, focus must remain confined inside it. If the user presses `Tab` and focus returns to a link in the background, the experience is broken.

### Keyboard Management
A "AAA" (highest WCAG standard) modal must meet precise expectations:
* **ESC:** Immediately closes the modal.
* **Initial Focus:** Focus should be placed on the first interactive element (often the close button or main field).
* **Restore Focus:** upon closure, focus must return to the button that opened the modal.

### Design Tip: Visible Focus
Do not remove `outline: none`. Instead, use `:focus-visible` to create a stylized indicator that only appears for keyboard users, preserving aesthetics for mouse users.

## 2. Drag & Drop: Beyond the Mouse

"Drag and Drop" is by essence a visual and motor interaction. However, it is entirely possible to make it accessible without changing the "Apple-like" look.

### Communication via ARIA-Live
When a user moves an element, the screen reader must be visually informed of what is happening.
* "Element selected, position 1 of 5."
* "Element moved to position 3."

### The Keyboard Alternative
The trick is to allow movement via arrow keys after activating "move" mode with `Space` or `Enter`.

## 3. Summary of WCAG Requirements for Components

| Feature | ARIA Role | Keyboard Behavior | Visual Feedback |
| :--- | :--- | :--- | :--- |
| **Modal** | `role="dialog"` | Tab (trap), ESC (close) | Dark overlay, clear focus |
| **Drag & Drop** | `aria-dropeffect` | Arrows (move), Space (grab) | Cursor change, shadow |
| **Tooltips** | `role="tooltip"` | Focus / Hover | High contrast (4.5:1 ratio) |

### Before / After: The Code Impact

A concrete example is worth a thousand words. Here is how to make a simple "X" button accessible.

#### ❌ BEFORE (Inaccessible)
The screen reader will simply read "button", without context.

```tsx
<button className="p-2 bg-red-500 rounded">
  <IconX />
</button>
```

#### ✅ AFTER (Accessible)
The reader will read "Close modal".

```tsx
<button
  className="p-2 bg-red-500 rounded"
  aria-label="Close modal"
  onClick={closeModal}
>
  <IconX aria-hidden="true" />
</button>
```

## 5. Beyond Divs: Semantic HTML

The first accessibility tool is not ARIA, it's HTML.
A `<div>` says nothing. A `<nav>` says everything.

### Landmarks
Screen readers allow jumping from one section to another.
* `<main>`: Main content (unique per page).
* `<nav>`: Major navigation links.
* `<aside>`: Complementary content (sidebar, ads).
* `<article>`: Content that stands alone (blog post, tweet).

Replacing your divs with these tags instantly improves your page navigability by 50%.

## 6. Focus Management in a SPA

This is THE problem with React/Next.js applications.
When you change page (route), the browser doesn't reload. Focus often gets "lost" on the `body` or on the last clicked button (which might have disappeared).

### The "Skip Link" and Reset Technique
On every route change, you should ideally reset focus to the main title (`h1`) or a focusable `<main>` container.

```tsx
// Simple example in a route useEffect
useEffect(() => {
  const main = document.getElementById('main-content');
  if (main) {
    main.focus();
  }
}, [pathname]); // Triggers when URL changes
```

Without this, the keyboard user has to tab through everything from the start on every click.
