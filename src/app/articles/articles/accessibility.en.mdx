A common misconception persists in the web development world: an accessible site must necessarily be "ugly" or stripped down. In 2026, with the tools we have, it is a myth that it is time to deconstruct.

Accessibility is not a checklist of constraints that curb your creativity, it is a framework that pushes for smarter and more robust design. Let's see how to manage two of the most complex components: the **Modal** and **Drag & Drop**.

---

## 1. The Modal: Taming the focus

A poorly designed modal is an insurmountable wall for a user navigating with a keyboard or screen reader. To be accessible, it must follow three golden technical rules.

### The Focus Trap
When a modal is open, the focus must remain confined inside it. If the user presses `Tab` and the focus returns to a link in the background, the experience is broken.

### Keyboard Management
A "AAA" modal (highest WCAG standard) must meet precise expectations:
* **ESC:** Immediately closes the modal.
* **Initial Focus:** Focus should be placed on the first interactive element (often the close button or the main field).
* **Restore Focus:** On closing, focus must return to the button that opened the modal.

### Design Tip: Visible Focus
Do not remove `outline: none`. Instead, use `:focus-visible` to create a stylized indicator that only appears for keyboard users, thus preserving the aesthetic for mouse users.

## 2. Drag & Drop: Beyond the mouse

"Drag and Drop" is essentially a visual and motor interaction. However, it is quite possible to make it accessible without changing the "Apple-like" look.

### Communication via ARIA-Live
When a user moves an item, the screen reader must be verbally informed of what is happening.
* "Item selected, position 1 of 5."
* "Item moved to position 3."

### Keyboard Alternative
The trick is to allow movement via arrow keys after activating "move" mode with `Space` or `Enter`.

## 3. Summary of WCAG Requirements for Components

| Feature | ARIA Role | Keyboard Behavior | Visual Feedback |
| :--- | :--- | :--- | :--- |
| **Modal** | `role="dialog"` | Tab (trap), ESC (close) | Dark overlay, clear focus |
| **Drag & Drop** | `aria-dropeffect` | Arrows (move), Space (grab) | Cursor change, shadow |
| **Tooltips** | `role="tooltip"` | Focus / Hover | High contrast (4.5:1 ratio) |

### Before / After: The impact of code

A concrete example is worth a thousand words. Here is how to make a simple "X" button accessible.

#### ❌ BEFORE (Inaccessible)
The screen reader will simply read "button", without context.

```tsx
<button className="p-2 bg-red-500 rounded">
  <IconX />
</button>
```

#### ✅ AFTER (Accessible)
The reader will read "Close modal".

```tsx
<button
  className="p-2 bg-red-500 rounded"
  aria-label="Close modal"
  onClick={closeModal}
>
  <IconX aria-hidden="true" />
</button>
```

## 4. Beyond Divs: Semantic HTML

The first tool of accessibility is not ARIA, it is HTML.
A `<div>` says nothing. A `<nav>` says everything.

### Landmarks
Screen readers allow jumping from one section to another.
* `<main>`: The main content (unique per page).
* `<nav>`: Major navigation links.
* `<aside>`: Complementary content (sidebar, ads).
* `<article>`: Independent content (blog post, tweet).

Replacing your divs with these tags instantly improves the navigability of your page by 50%.

## 5. Focus Management in a SPA

This is THE problem with React/Next.js applications.
When you change pages (route), the browser does not reload. Focus often remains "lost" on the `body` or on the last clicked button (which may have disappeared).

### The "Skip Link" and Reset Technique
Ideally, on every route change, you should reset focus to the main title (`h1`) or a focusable `<main>` container.

```tsx
// Simple example in a route useEffect
useEffect(() => {
  const main = document.getElementById('main-content');
  if (main) {
    main.focus();
  }
}, [pathname]); // Triggers when URL changes
```

Without this, the keyboard user has to tab through everything from the beginning at every click.
