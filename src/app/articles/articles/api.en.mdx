Choosing how your data flows between client and server is one of the most critical decisions of a project. It is the nervous system of your application.

As a Full-stack dev, I like to see APIs as types of conversations. Sometimes you want a formal report, sometimes a simple SMS, and sometimes a phone call that never ends.

---

## 1. REST: The Standard (The Registered Letter)

This is the basis of the modern Web. Each URL is a resource. It is robust, predictable, and everyone understands it.

**The conversation:**
> **Client:** "Hi! I am user X, here is my JWT token. I would like the data for page `/dashboard/profile`."
>
> **Server:** "That's in order. Here is the complete JSON object with your name, email, your 50 account settings, and history (even if you only asked for the name)."

* **Ideal for:** Classic CRUD, e-commerce sites, blogs.

---

## 2. Polling: "Are We There Yet?"

When the server needs time to process info, the client must check if it's ready.

### A. Short Polling (The Impatient Child)
We send a request every X seconds.
> **Client:** "Is the report ready?" -> **Server:** "No."
> **Client (2s later):** "Is the report ready?" -> **Server:** "No."
> **Client (4s later):** "Is the report ready?" -> **Server:** "Yes, here it is."

### B. Long Polling (The Holding Line)
The server keeps the request open until it has an answer.
> **Client:** "I'm looking for info, I'm staying on the line, answer me as soon as it's ready."
> **Server:** *(Waits 20 seconds...)* "Here, here is the info!"

---

## 3. GraphQL: The "Personal Shopper"

Why retrieve a whole JSON when you only want a first name? GraphQL allows the front-end to dictate its needs.

**The conversation:**
> **Client:** "Hi, I just want the `username` and `photo_url` of ID #42. Nothing else."
>
> **Server:** "No problem. Here is an object with exactly those two fields. We save bandwidth!"

* **Ideal for:** Complex dashboards, mobile apps (saves data).

---

## 4. WebSockets: The Open Line (The Phone)

Here, we don't close the door. We establish a persistent bidirectional connection.

**The conversation:**
> **Client:** "I'm connecting to the trading channel."
>
> **Server:** "OK, the line stays open. I'll send you Bitcoin prices every second, and you send me your buy orders whenever you want."

* **Ideal for:** Trading, Chat, Video Games, Collaborative Tools (Figma-like).

---

## 5. SSE (Server-Sent Events): The Radio

It's like WebSockets, but one-way: server to client. It's lighter and runs on standard HTTP.

**The conversation:**
> **Client:** "I'm subscribing to score notifications."
>
> **Server:** "Works. Don't say anything, I'll push you info as soon as there's a goal."

* **Ideal for:** Price feeds, push notifications, live feeds.

---

## 6. Webhooks: "Don't Call Me, I'll Call You"

It's the reverse of a classic API. The server (often third-party) sends data to your server as soon as an event occurs.

**The conversation:**
> **Stripe (Third-party Server):** "Hey, your client just paid their invoice! I'm sending you details to your endpoint `/api/webhook` so you can update your database."
>
> **Your Server:** "Received! Processing it right away."

---

## 7. gRPC: Formula 1 (High Performance)

Widely used in microservices or Web3 for speed. We use "Protocol Buffers" (binary) instead of JSON (text).

**The conversation:**
> **Microservice A:** *(Sends ultra-compressed and typed binary packet)* "Calculate-this-fast."
>
> **Microservice B:** *(Responds instantly in binary)* "Here-is-the-result."

---

## 8. Practical Case 2026: Server Actions & tRPC

With the advent of **React Server Components (RSC)**, the boundary between click and request blurs.

### Server Actions: The "Magic" Method
No more manually declaring API routes. You import a server function directly into your client component.

```tsx
// actions.ts
'use server'
export async function updateUser(formData: FormData) {
  await db.user.update(...)
}

// Button.tsx
import { updateUser } from './actions'
<form action={updateUser}>
  <button>Save</button>
</form>
```
* **Advantage:** Blazing fast dev speed. No glue code.
* **Disadvantage:** Hard to expose to external clients (Mobile, Public).

### tRPC: The "Type-Safe" Method
If you love TypeScript, tRPC is a religion. The backend exports its types, and the frontend consumes them. If you change a field name server-side, your IDE turns red client-side instantly.

### Modern Stack Comparison

| Criterion | Classic REST API | Next.js Server Actions | tRPC |
| :--- | :--- | :--- | :--- |
| **Typing** | Manual (Zod/Swagger) | Automatic (Partial) | 🚀 Perfect (End-to-end) |
| **Dev Speed** | 🐢 Slow | 🚀 Very Fast | 🐇 Fast |
| **Payload** | Heavy JSON | Optimized Binary (RSC) | Optimized JSON |
| **External Client** | ✅ Easy | ❌ Complicated | 🟠 Possible but specific |

## 9. Security: Rate Limiting & Auth

Opening an API means opening a door. You need a bouncer.

### Rate Limiting (The Bouncer)
Preventing a script from spamming your API is vital.
In the Serverless world (Vercel/Cloudflare), we often use **Upstash (Redis)** to implement a "Leaky Bucket".

```tsx
// Next.js Middleware (Conceptual)
import { Ratelimit } from "@upstash/ratelimit";

const ratelimit = new Ratelimit({
  redis: Redis.fromEnv(),
  limiter: Ratelimit.slidingWindow(10, "10 s"), // 10 requests per 10s
});

export async function middleware(req) {
  const ip = req.ip ?? "127.0.0.1";
  const { success } = await ratelimit.limit(ip);

  if (!success) {
    return new Response("Too many requests", { status: 429 });
  }
}
```

### Auth: JWT vs Session (The Eternal Debate)
With Next.js App Router, the trend is returning to **Sessions (HttpOnly Cookies)** managed by libraries like **Lucia Auth** or **NextAuth v5**. Why?
* **JWT (Stateless):** Good for microservices, but hard to revoke easily.
* **Session (Database):** Safer, instant revocation (ideal for a "Log out of all devices" button).

---

## Conclusion: What to Choose for Your Portfolio?

If you develop with **Next.js**, the winning combination is often:
1. **REST / Server Actions** for 90% of cases.
2. **Webhooks** to handle payments (Stripe) or auth (Clerk/Auth0).
3. **SSE or WebSockets** if you add a small real-time feature.

The secret of a good dev is not knowing the most "hype" tech, but using the one that solves the problem with the least unnecessary complexity!
