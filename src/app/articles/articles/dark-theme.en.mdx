Dark mode is no longer a "nice option", it is a baseline expectation. But implementing it poorly can harm the user experience, especially with the famous **FOUC** (*Flash of Unstyled Content*): that violent white flash that occurs for a few milliseconds before JavaScript detects your preferences.

In 2026, we have native tools to solve this cleanly.

---

## 1. The Foundation: `color-scheme`

Even before writing your first CSS variable, you must inform the browser that your site supports both modes. This allows the browser to adapt native elements (scrollbars, default buttons, forms).

```css
:root {
  /* Tells the browser that the site supports both modes */
  color-scheme: light dark;
}
```

This simple line changes the game: if the user is in dark mode, the default page background becomes black and the text white, even before your CSS is fully loaded.

---

## 2. The Revolution: The `light-dark()` Function

Forget complex and long `.dark-mode` selectors. Modern CSS offers us the `light-dark(light-value, dark-value)` function.

```css
:root {
  --bg-color: light-dark(#ffffff, #0f172a);
  --text-color: light-dark(#1e293b, #f8fafc);
  --accent: #3b82f6;
}

body {
  background-color: var(--bg-color);
  color: var(--text-color);
}
```

The browser automatically chooses the correct value based on the element's `color-scheme` property. It's clean, readable, and ultra-performant.

---

## 3. Avoiding the "White Flash" in Next.js

The flash problem occurs when the server renders "neutral" (white) HTML and the client has to wait for JS loading to apply the `.dark` class.

### The 2026 Solution: The Critical Blocking Script

The most reliable method remains injecting a small inline script into the `<head>` of your `layout.tsx`. This script runs **before** the rest of the page is drawn.

```tsx
// In your RootLayout
<head>
  <script
    dangerouslySetInnerHTML={{
      __html: `
        try {
          if (localStorage.theme === 'dark' || (!('theme' in localStorage) && window.matchMedia('(prefers-color-scheme: dark)').matches)) {
            document.documentElement.classList.add('dark')
          } else {
            document.documentElement.classList.remove('dark')
          }
        } catch (_) {}
      `,
    }}
  />
</head>
```

Thanks to Next.js **Server Components**, this script is sent as-is in the initial HTML, guaranteeing an invisible transition.

## 4. Architecture: "Semantic Tokens"

Never hardcode hex colors in dark mode (#000). Use an abstraction layer.

### Level 1: Primitive Tokens
This is your raw palette.
```css
:root {
  --blue-500: #3b82f6;
  --slate-100: #f1f5f9;
  --slate-900: #0f172a;
}
```

### Level 2: Semantic Tokens (Abstract)
This is what you use in your components. They change according to the theme.
```css
:root {
  --bg-primary: var(--slate-100);
  --text-primary: var(--slate-900);
}

[data-theme='dark'] {
  --bg-primary: var(--slate-900);
  --text-primary: var(--slate-100);
}
```

**Advantage:** If tomorrow you want to change your brand's "Blue", you only touch the Primitives. If you want to adjust dark mode contrast, you only touch Semantics.

## 5. Accessibility and Dark Mode

Dark mode is not just a question of aesthetics, it is also a question of visual comfort.

* **Contrasts:** Verify that your contrasts remain WCAG compliant in dark mode. Sometimes a blue that works well on white becomes unreadable on a dark gray background.
* **Images:** Remember to slightly reduce the brightness of overly bright images in dark mode so as not to dazzle the user.

```css
.dark img {
  filter: brightness(0.8) contrast(1.1);
}
```

## Conclusion

In 2026, theme management must be **invisible**. By combining the power of Next.js for critical script injection and new CSS functions like `light-dark()`, we get a robust, performant system that respects user preferences.

Your site should not just "have a dark mode", it should "be designed for light and darkness".
