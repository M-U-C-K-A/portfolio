Translating a site isn't just about replacing "Bonjour" with "Hello". It is an architectural challenge that impacts routing, SEO, performance, and above all user experience.

In 2026, with the Next.js App Router, internationalization (i18n) has become more structured, but demands rigorous configuration to remain performant.

---

## 1. Routing: Why `/fr` is Indispensable

There are several ways to handle language (cookies, local storage, headers). However, for SEO, URL structure is the only viable method.

* **Sub-paths (Recommended):** `mysite.com/fr` or `mysite.com/en`.
* **Domains:** `mysite.fr` or `mysite.com`.

Using sub-paths allows search engines to index each version of your page independently. Next.js facilitates this thanks to **Middleware**, which intercepts the request, detects the browser language, and redirects the user to the correct prefix if necessary.

---

## 2. The Middleware: The Conductor (Concrete Example)

This is where the magic happens. The middleware intercepts every request to direct the user to the right language.

```typescript
import createMiddleware from 'next-intl/middleware';

export default createMiddleware({
  // A list of all supported locales
  locales: ['en', 'fr'],

  // If no locale matches, use this one
  defaultLocale: 'fr',

  // Redirect / to /fr
  localePrefix: 'always'
});

export const config = {
  // Match only internationalized pages
  matcher: ['/', '/(fr|en)/:path*']
};
```

This simple configuration automatically handles browser language detection and 307 redirects.

## 3. Organizing Dictionaries: Typing First

The classic mistake is using simple JSON objects without protection. As a full-stack developer, you want TypeScript to yell at you if you forget a translation key in one language.

### Recommended Structure
```text
messages/
  en.json
  fr.json
```

### Strict Translation Typing

By using libraries like `next-intl` or `i18next`, you can link your JSON files to your types:

```typescript
// Example of typed component
import { useTranslations } from 'next-intl';

export function LoginButton() {
  const t = useTranslations('Auth');

  // TypeScript will validate that 'login_label' exists in fr.json and en.json
  return <button>{t('login_label')}</button>;
}
```

## 4. SEO and Accessibility: The Forgotten Ones of i18n

Translating the interface is good, but don't forget technical metadata.

1. **The `lang` attribute:** Your `<html lang="fr">` tag must change dynamically. It is crucial for screen readers (Accessibility) so they use the correct voice synthesis.
2. **`hreflang` tags:** They indicate to Google the relationship between your pages. If I am on the French "About" page, the `hreflang` tag must point to the English "About" version.

## 5. Dates, Numbers, and Currencies: The Intl API

Never translate dates or currencies manually. The browser and Node.js process an ultra-powerful native API: `Intl`.

```javascript
const price = 1250.50;
new Intl.NumberFormat('fr-FR', { style: 'currency', currency: 'EUR' }).format(price);
// Result: 1 250,50 €

new Intl.NumberFormat('en-US', { style: 'currency', currency: 'USD' }).format(price);
// Result: $1,250.50
```

## 7. International SEO: The Devil is in the Details

Having a `/fr` and an `/en` isn't enough. Google must understand the link between them.

### Hreflang & Canonicals
`next-sitemap` or `next-seo` don't always handle this perfectly.
Ensure your `<head>` contains:
```html
<link rel="alternate" hreflang="en" href="https://site.com/en/blog" />
<link rel="alternate" hreflang="fr" href="https://site.com/fr/blog" />
<link rel="alternate" hreflang="x-default" href="https://site.com/en/blog" />
```
Without the `x-default`, Google might ignore your pages for users who speak neither FR nor EN.

### Localized Images
It is often forgotten: show a screenshot of the EN interface for English speakers, and FR for French speakers.

```tsx
const screenshot = locale === 'fr' ? '/img/app-fr.png' : '/img/app-en.png';
<Image src={screenshot} alt={t('screenshot_alt')} />
```
This kind of detail increases your conversion rate by 15%.
